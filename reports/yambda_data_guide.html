Getting the data and using it

Everything you need to start: what the project asks, how to download and check the data, what the files contain, and what each of the two teams has to build and answer. No earlier results are assumed.

Main question
For the same users, is what the recommender plays broader or narrower than what the users choose themselves?

Section 1

The problem in short

Yambda is a log of real listening on Yandex Music. All IDs are anonymous, so we know what was played, when and how it reached the user, but not what the music is.

The key flag

is_organic

1 = the user chose the track (organic stream). 0 = the recommender served it (recommended stream). Our whole comparison is organic vs recommended, for the same users.

Caveat to settle

"Organic" is not pure taste

A track first discovered through a recommendation and replayed later is organic the second time. Decide, and state in the report, whether you count first discovery only or every play.

What we can and cannot do

We can
  • Compare the two streams for the same users
  • Measure variety by artist ID
  • Describe the sound of a track with its 128-number audio embedding
  • Group listens into sessions and study what is played together
  • Use likes, dislikes and percent played as feedback
We cannot
  • Name an artist or track, or check one by ear
  • Get real genres. We can only build pseudo-genres from sound or from co-listening.
  • See what was shown but ignored (no impressions)
  • Know the recommender algorithm, or anything about the users
  • Use calendar time. Timestamps are seconds since the start of the log.
  • Claim causes. Users who accept recommendations may differ from those who do not.

The two teams

Team 1 · RQ4

Are pseudo-genres real structure in the data, or just an artefact of the clustering method? Compare a sound-based grouping with a graph-based one.

Team 2 · RQ2 + RQ3

Do recommendations make users more alike, and which tracks are played together? Two linked questions, answered with similarity search and frequent itemsets.

Section 3

Download the data

The dataset is yandex/yambda on Hugging Face (Apache 2.0). The script pins one revision (dd6f3a19…448), so everyone gets identical files. An interrupted download resumes when you re-run the script.

  1. Download events and mappings (about 477 MB). 
    python scripts/download_yambda.py
    Files land in data/raw/yambda/. This is enough to build the shared tables in section 5.
  2. Get the audio embeddings. Only one person downloads the 13.8 GB file. Yambda-50M uses about 848k of its 7.7M tracks. That person runs: 
    python scripts/download_yambda.py --embeddings
python scripts/extract_embeddings_50m.py
    The second command takes a few minutes and about 1–2 GB RAM. It writes three files to data/processed/. Everyone else copies that folder and skips the big download. In practice you need only emb50m_item_ids.npy and emb50m_norm.npy.
  3. Verify. Compare the file sizes with the table and the counts below.

Things to know before you touch it

Timestamps

Whole seconds since the start of the log, in steps of 5, from 0 to 26,000,000 (about 301 days). A 30-minute gap is therefore 1800.

Percent played

played_ratio_pct is not capped at 100. It reaches 159 in the data, and 0 is possible. A filter of ≥ 50 keeps about 63% of listens.

Memory

About 15 GB RAM, and about 5.5 GB free with other apps open. Read only the columns you need (pq.read_table(path, columns=[...])) and keep one job under about 8 GB.

Gaps

About 3% of listens have no embedding, and about 0.02% have no artist. Drop them in the steps that need them, and report how many.

Section 5

Shared tables both teams build on

Both teams start from the same two derived tables. If each builds its own, the numbers will not match. One person builds them first, then everyone reads them.

Table 1

Real listens, listens_50m.parquet

Only event_type = listen and played_ratio_pct ≥ 50 (a track played at least halfway counts as a real listen). Columns: uid, item_id, timestamp, is_organic.

Table 2

Sessions, sessions_50m.parquet

Table 1 cut per user into sessions: a new session starts when the gap to the previous listen exceeds 30 minutes (1800 s). Columns: uid, session_id, item_id, timestamp, is_organic.

Open decision

A session can contain both organic and recommended listens. Decide once, as a team, how that is handled: assign each session to the stream of most of its listens, split it into two baskets, or drop mixed sessions. Check how many sessions are mixed before choosing, and write the choice down.

Why shared

Team 2 uses the sessions as baskets for frequent itemsets, and Team 1 uses them to build the co-listening graph. Table 1 gives Team 2 its user track sets.

Section 6

What each team builds

Each question is answered with two methods, then you compare what they say. If they agree, the finding is stronger. If they disagree, that is a result too.

Team 1RQ4

Are the pseudo-genres real structure, or an artefact of k-means?

There are no genre labels, so any "genre" we use is made by a clustering method. If a different method gives a very different grouping, the genres are not trustworthy.

Inputs

  • emb50m_norm.npy + emb50m_item_ids.npy for the sound grouping, sessions_50m.parquet for the graph, artist_item_mapping if you use artist nodes.

Method A · spherical k-means on the embeddings

  • Write k-means that uses cosine similarity on the normalised vectors (re-normalise each centre after every update). Start with k = 32, and try a few other values.
  • Check it against scikit-learn k-means on the same data (same inertia or mean cosine, similar partition by ARI).
  • With millions of points, fit on a random sample and assign the rest.
  • Save the labels as kmeans_labels_50m.parquet (see section 7), since Team 2 needs them.

Method B · Louvain on a co-listening graph

  • Nodes are tracks (or artists). An edge connects two nodes that occur in the same session of the same user, weighted by how often.
  • Prune first. About 848k tracks is too large for a plain run. Keep the top N by listens, or use artist nodes, and require a minimum edge weight.
  • Louvain is not deterministic, so run several seeds and a few resolution values.

What to compare

  • Agreement between the two groupings on the tracks both cover: ARI, NMI, overlap.
  • A reference scale for those numbers: a random partition with the same sizes, and k-means against k-means with a different seed. Without these, nobody can tell whether a given ARI is high.
  • Then the link to the main question: take the diversity measure of your choice (distinct genres per user in each stream), compute it with k-means genres and with Louvain genres, and see whether the organic-vs-recommended conclusion changes.

Pitfalls

  • Tracks outside the pruned graph have no community. Report coverage and compare only on shared tracks.
  • Build pairs inside one session of one user, never across users.
  • Build the graph from organic sessions first, and the recommended ones second. A recommender can shape co-listening by itself.
Team 2RQ2 + RQ3

Do recommendations make users more alike, and which tracks are played together?

How the two questions connect: RQ2 says how alike users are, RQ3 says which track pairs are played together. A natural joint question: do the pairs behind the frequent itemsets also explain the user similarity, and do they lie in the same region of sound space?

Inputs

  • listens_50m.parquet (user track sets per stream), sessions_50m.parquet (baskets), emb50m_norm.npy + emb50m_item_ids.npy (sound), and Team 1's kmeans_labels_50m.parquet for the pair-to-genre link.

RQ2 · Method A · MinHash / LSH on track sets

  • For each user and stream, one set of distinct tracks. Two users are similar if their sets overlap (Jaccard similarity).
  • MinHash compresses each set to a short signature. LSH bands those signatures so likely-similar pairs collide, without comparing all pairs.
  • Write both yourself. Build an exact Jaccard baseline on a subset of users to measure the recall of your LSH, and tune the number of bands and rows.
  • Use only users with enough real listens in both streams (choose a minimum such as 50, and report how many users that leaves).

RQ2 · Method B · cosine on sound profiles

  • The profile of a user in a stream is the mean normalised embedding of their tracks. Users are similar if the profiles point the same way.
  • Optional: for each user, the nearest neighbour ("twin") in each stream.

RQ3 · Method A · frequent itemsets (A-Priori / PCY)

  • Sessions are baskets of tracks. Find frequent single tracks, then frequent pairs, with their support and lift, separately per stream.
  • PCY adds a hash table in the first pass to throw out pairs that cannot be frequent. Write A-Priori first, then PCY, and check that both give identical frequent pairs.
  • Compare the streams fairly: equal numbers of baskets, and similar basket-size distributions.

RQ3 · Method B · sound neighbours and session coherence

  • Coherence = mean pairwise cosine similarity of the tracks within one session, averaged per stream.
  • For the top frequent pairs, ask whether the two tracks are close in sound, and whether they share a pseudo-genre more often than random pairs do.

Where they meet

  • Do user pairs that LSH finds similar share frequent pairs? Does the user similarity change when you remove the tracks that occur in frequent pairs?
  • For the same user pairs, compare similarity by shared tracks with similarity by sound.

Pitfalls

  • Frequent pairs are often driven by popular tracks. Report lift next to support.
  • Very large numbers of users make tiny differences look "significant". Report effect sizes with intervals.
  • Users and sessions are in the same data, so do not treat sessions of one user as independent samples without saying so.

Every saved result carries the dataset size (50M), the settings (k, resolution, seed, LSH bands and rows, support threshold) and the run date, either as columns or in the file name.

Dependency

Section 8

Rules for everyone

Fair comparison

  • Real listens only (≥ 50% played)
  • Count each distinct track once, not every play
  • Same users in both streams
  • Equal sample sizes and basket sizes

Honest reporting

  • Effect sizes and intervals next to p-values
  • Associations, not causes
  • Pseudo-genres are not real genres
  • Say how replays of recommended tracks are handled

Working

  • Write your own method, then check it against a library
  • Shared code in one module, notebooks only plot
  • One heavy job at a time
  • Read only needed columns
